# 复盘：xyz:SKHYNIX Oracle 异常事件（2026-07-28）

> 本文基于公开报道与 HIP-3 协议文档重建，数字以第三方报道为准（见文末来源）。
> 目的不是追责，而是把这次 $57.4M 的事故拆成可以被守卫拦截的环节——每一条启示都对应本库的一个模块。

## 一、事故速览

| 项 | 值 |
|---|---|
| 市场 | xyz:SKHYNIX（SK 海力士美股化永续，Trade.xyz 部署） |
| 日期 | 2026-07-28（韩国时间上午，KRX 开盘前） |
| 触发源 | 韩国 NXT 交易所盘前市场**一笔**成交：1,272,000 KRW |
| 参照 | KRX 上一交易日收盘 1,785,000 KRW → 隐含 **-28.7%** |
| 永续表现 | 标记价格被打到 discovery bound 附近，合约一度下跌 ~17.9-19% |
| 后果 | **$57.4M 清算，960 个账户**；获利空头遭 ADL |
| 结局 | Trade.xyz **自愿全额赔付**全部清算损失；罚没窗口未关闭 |

平摊下来，每个被清算账户平均损失约 $60k。

## 二、机制拆解：三个输入，两个握在部署方手里

HIP-3 的标记价格由三个输入取中位数合成：

1. **链上中位价**（Hyperliquid 提供）：本链最近成交、买一卖一的中位数——协议控制的唯一输入
2. **部署方推送的 oracle/mark 价**——部署方控制
3. **部署方推送的 external perp 价**——部署方控制

Hyperliquid 官方举的例子直白到冷酷：假设链上中位价是 100，部署方推 150 和 151，标记价格就是 150——**部署方的数字赢了**。xyz 未设独立 oracleUpdater（用部署方密钥直接推送），三个输入里实际是"一个协议 + 两个自己"。

事故链：

```
NXT 盘前 1 股成交 @ 1,272,000 KRW
  ↓ 被喂价通道视为有效输入
部署方 oracle 输入换算美元后暴跌 ~28.7%
  ↓ median(链上价, 部署方输入×2) = 部署方输入
标记价格崩向 discovery bound
  ↓ bound 将跌幅限制在 ~19%（SKHYNIX 10x 杠杆档，亚洲个股 band ±10-20%）
960 个账户触及清算线 → $57.4M 清算
  ↓ SKHYNIX 是全仓保证金资产
亏损仓位吸走不相干押注的抵押品 → 获利空头 ADL
```

值得注意的背景：那天韩国股市本身在暴跌（KOSPI -10.84%，SK 海力士正股当日 -14.65% 收 155 万韩元）。**插针改变的不是方向，是清算的时间和价位**——多单在正股正式开盘前一小时，被一个仅一股成交、事后被证明不真实的价格提前出局。

## 三、防线为什么没拦住

1. **喂价通道没有输入卫生检查。**一笔盘前薄市成交（低流动性时段、单笔、交易所随后停牌）被当作有效价格源。问题是"新鲜"和"可信"被混为一谈了。
2. **discovery bound 是损失上限，不是防线。**bound 把 28.7% 的冲击限制在 19%，但它只决定"清算多深"，不决定"清算发生与否"。bound 触边本身就该是最高级别告警。
3. **验证者自动审查的阈值是 ±50%。**外部价较当日开盘波动超 50% 才触发跨保证金资产自动审查——19% 远低于此，没有任何机制性审查被启动。协议的应急阈值和市场的实际风险分布脱节。
4. **全仓保证金放大了传染。**同一平台上三星、现代用逐仓，SKHYNIX 用全仓——一个市场的坏价可以吸走交易者压在不相关押注上的抵押品。

## 四、罚没条款：为什么"自愿赔付"比"等罚没"更理性

HIP-3 罚没分档（验证者权益加权投票决定）：

| 输入性质 | 最高罚没 |
|---|---|
| 降低网络性能 | 质押的 20% |
| 短暂停机 | 50% |
| 无效状态转换 / 长时间中断 | **100%** |

三条关键性质：
- **不区分动机**：恶意、粗心、忠实执行一份糟糕的喂价设计——同等适用
- **烧毁而非分配**：罚没的 HYPE 直接销毁，960 个被清算账户一分钱拿不回来
- **长期暴露**：质押须锁 183 天，且 7 天解质押队列期内仍可被罚

罚没对 deployer 的实际威慑是：$27M+ 的质押暴露在"验证者投票"这个不确定过程里。Trade.xyz 选择自愿全额赔付、换取叙事主动权，正是对这种不确定性的理性定价——**对 deployer 来说，事故成本 = 赔付 + 声誉 + 可能的罚没，三者叠加**。守卫系统的价值就是把第一项和第三项的概率压到零。

## 五、守卫启示 → 本库模块映射

| 这次事故暴露的缺口 | 守卫模块 | 拦截方式 |
|---|---|---|
| 单笔薄市成交直接进 oracle | `deviation` | 跨场所交叉校验：外部输入 vs 多源中位数偏离超阈值即告警/拒绝 |
| 盘前/停牌时段照常喂价 | `offhours` | 时段感知：交易所停牌、盘前低流动性档位下切换到"最后有效价 + bound"模式 |
| bound 触边无告警 | `bounds` | 标记价格接近 band 边缘（如 90% 触发 re-anchor 参照）时逐级告警 |
| "新鲜"压倒"可信" | `staleness` | 停滞守卫的正确语义：宁可短暂滞后于最后有效价，也不吞下可疑的新鲜价 |
| 全仓传染无预警 | `halt-guard` | 事前：外部价 vs 开盘的移动逼近验证者 50% 审查线时报警；事中：haltTrading 决策核对 |
| 事后无复盘基础设施 | `monitor` | 全程只读采样留存，事故可逐 tick 重放 |

## 六、给 deployer 的一句话

你的喂价系统里每一个"上游报价"都是攻击面，每一个自动阈值都是别人的假设。SK Hynix 这 $57.4M 买的教训只有一句话：**在"把外部价格当真"之前，先问这笔价格是谁、在什么流动性下、以多大的单子形成的。**
